# ENABLE_CONVEX_CLOUD is one conceptual flag split across two systems

CHI-78 needed a fast way to cut Convex cloud usage during a free-tier cap incident. We use a single conceptual flag, `ENABLE_CONVEX_CLOUD`, but it's set and checked in two unrelated places because Convex and Vercel env vars are invisible to each other: as a **Convex** env var on the production deployment (`npx convex env set ENABLE_CONVEX_CLOUD false --prod`), read inside the three cron handlers (`smartMeterRegistryRefresh.doRefresh`, `israelPlacesRefresh.doRefresh`, `formSubmissionDeliveries.runBatch`) to no-op the recurring per-minute/weekly costs on the already-running production deployment; and as a **Vercel** env var on the Preview environment, read at the top of `vercel.json`'s `buildCommand` shell script, which fails the build outright before `npx convex deploy` ever runs — so a PR pushed during the incident never gets a new (or updated) preview Convex deployment at all. A Convex runtime env var can't gate a Vercel build step (no deployment exists yet to read it from), and a Vercel build-time env var can't gate an already-running production deployment's crons (the build step doesn't re-run just because crons fire) — hence two toggles under one name instead of one shared mechanism. The two are set and flipped independently; there is no code that keeps them in sync.

Scope is deliberately limited to production and to *new* preview deployments (including new pushes to already-open PRs, which now fail the same build check). Already-running preview deployments at the moment the incident starts are left alone — per ADR-0011 they're bounded and self-terminate when their PR closes, so that residual cost decays on its own without needing to be reached into.

## Considered Options

- **Single Convex-side flag only**: rejected — stops production's crons but can't prevent a new preview deployment from being created and deployed in the first place.
- **Single Vercel-side flag only**: rejected — stops new preview deploys but can't stop crons already running on production's existing deployment, since those don't re-evaluate any code on a new build.
- **Propagate the flag to every currently-open preview deployment too**: rejected — previews are bounded and self-terminate on PR close (ADR-0011), so it's not worth the complexity of scripting writes across an unknown number of existing deployments for a rare, incident-only mechanism.
