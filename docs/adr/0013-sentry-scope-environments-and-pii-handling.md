# Sentry integration: scope, environments, and PII handling

> See [`docs/sentry-integration-diagram.md`](../sentry-integration-diagram.md) for an architecture diagram.

CHI-40 calls for Sentry integration with no further detail, so the scope had to be decided from scratch. We're integrating Sentry across both runtimes — the Astro/React frontend and the Convex backend — as **four** separate Sentry projects: `chisko-prod-fe`, `chisko-prod-be`, `chisko-dev-fe`, `chisko-dev-be`. Each has error monitoring, performance tracing, and session replay enabled. The dev projects receive events from every non-prod (per-PR preview) deployment — there's no per-PR Sentry project, mirroring the per-PR-ephemeral-but-shared-dev-tooling pattern already used for things like the weekly registry-refresh cron. Non-prod events are not gated off; catching a bug in a PR preview before merge is worth the noise, since previews are already isolated per-PR per ADR-0011. Each runtime still sets an `environment` tag (`preview` vs `production`) on top of the project split, mainly so dev-project events stay attributable to a deployment context even though they're not separated by Sentry project. Source maps are uploaded at build time via the Sentry Vite plugin (bundled with `@sentry/astro`, configured in `astro.config.mjs`), and the frontend release is tagged with the git SHA (`VERCEL_GIT_COMMIT_SHA`, threaded to the frontend bundle via a Vite `define`), so production stack traces resolve to real file/line info. The backend does **not** get an automated per-commit release tag: an earlier version of this ADR threaded the SHA to Convex via a `npx convex env set SENTRY_RELEASE ...` build step, but that broke every deploy — `CONVEX_DEPLOY_KEY` (both prod and preview, per ADR-0011) is a fixed-capability service token that can deploy code but cannot call admin-API operations like `WriteEnvironmentVariables`, the same class of limitation ADR-0012 hit with `RunInternalActions`. `convex/lib/sentry.ts` still reads `SENTRY_RELEASE` from the environment and tags it when present (see CHI-41), so it can be set manually via the Convex dashboard if backend release tracking becomes worth the effort — it just isn't wired to the commit SHA automatically today.

PII must be scrubbed before anything reaches Sentry — request bodies, extra context, and breadcrumb data are recursively redacted by key name (`name`, `phone`, `email`, `street`, `houseNumber`, `placeOfResidence`) client- and server-side rather than relying on Sentry's generic default scrubbers. Session replay relies on the Replay integration's defaults (`maskAllText`, `blockAllMedia`), which mask all on-screen text and block all media by default — covering bill upload, address, and contact forms without needing custom per-component selectors. This follows directly from the Data Retention and Consent model already documented in `CONTEXT.md`: those commitments govern how this app handles user data, and a third-party error tracker holding unredacted bill/contact data on its own retention schedule would violate them.

On the backend, only Convex actions and httpActions report to Sentry, via a `convex/lib/sentry.ts` helper (`captureException`, and a `withCapturedExceptions` wrapper to avoid repeating the same try/catch six times) in catch blocks (`billImports.ts`, `israelPlacesRefresh.ts`, `http.ts`, `internal/seedAll.ts`, `internal/deployHooks.ts`, `smartMeterRegistryRefresh.ts`). The helper posts directly to Sentry's ingest API via `fetch` rather than using `@sentry/node`, since most of these functions run in Convex's default V8 isolate (no Node built-ins) rather than the `"use node"` runtime. Queries and mutations run in a deterministic V8 isolate with no network access, so they cannot call Sentry directly — their errors remain visible only in Convex's own dashboard. We considered Convex Log Streams (which would also cover queries/mutations by forwarding all function logs to Sentry at the platform level), but rejected it for now: Log Streams forwards raw log/exception output with no redaction hook, which conflicts with the PII-scrubbing decision above, and would need its own provisioning automation per ephemeral per-PR Convex deployment (paralleling the self-seeding work in ADR-0012) — a bigger lift than this issue calls for.

Session replay's session sample rate is set to 0 with error sample rate at 1.0 (replay only on sessions that error), since Sentry's free tier caps replays at 50/month regardless of plan tier — a session-based sample rate would exhaust that quota almost immediately under any real traffic. Alert rules (Slack/email notifications) are explicitly out of scope for this issue; they're a dashboard config, not code, and are easier to tune after seeing real signal volume.
